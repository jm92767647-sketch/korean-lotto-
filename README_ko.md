# 로컬 로또 웹앱

서버 계산, 외부 API, 로그인, CDN 없이 동작하는 순수 HTML/CSS/JavaScript 앱입니다. 8,145,060개 전체 조합, 고정 필터 5개, 실제 C4/C5 합집합, 전체 후보 greedy, 전수 1장 교체 local search, 다중 초기화, 전체 U 독립 검산을 구현했습니다.

## PC에서 가장 간단히 실행하기

ZIP을 풀고 `lotto-webapp/index.html`을 Chrome 또는 Edge에서 여세요. **폴더 안의 파일들을 함께 보관**해야 합니다. 인터넷 연결이나 Python 설치는 필요하지 않습니다. Web Worker는 이미 로드된 코드에서 Blob으로 만들므로 `file://`에서 Worker 파일을 별도로 불러오는 제한을 피합니다. 파일 보안 정책이 Worker 실행을 차단하는 환경에서는 아래 정적 파일 실행 방식을 사용하세요.

1. 직전 회차 본번호 6개를 입력합니다. 보너스는 제외합니다.
2. ‘최적 10게임 생성’을 누릅니다.
3. 계산 중 화면을 열어두세요. ‘계산 중단’은 즉시 Worker를 종료합니다.
4. ‘10게임 전체 복사’ 또는 ‘결과 저장’을 이용합니다. 최근 결과는 가능하면 브라우저 localStorage에 자동 저장됩니다.

예시 입력 버튼은 **11 13 19 20 31 44**를 넣습니다. 요청문에 실제 번호가 없어서 기존 예시를 테스트에 사용했습니다. 최신 회차를 조회하지 않습니다.

기본 설정은 Python과 같이 기준 초기해 1개 + 추가 2개입니다. ‘기본 1회’도 전체 후보 greedy와 local search를 끝까지 수행합니다. 후보를 샘플링하거나 랜덤 번호만 생성하는 모드는 없습니다.

## iPhone Safari에서 실행하기 — 초기 전달과 오프라인 실행의 차이

**iPhone 파일 앱에서 HTML을 누르면 Safari가 아니라 미리보기로 열릴 수 있습니다. 이 미리보기에서 JavaScript·Worker 앱 실행을 보장할 수 없습니다.** iPhone에 ZIP만 복사한 뒤 파일 앱에서 누르는 동작을 ‘Safari PWA 설치’와 동일하다고 설명할 수는 없습니다.

Safari에서 페이지를 정상적으로 한 번 전달받는 방법과, 이후 오프라인에서 실행하는 방법을 구분해야 합니다.

### A. PWA: 초기 한 번 HTTPS로 열고 이후 오프라인 사용

1. 이 폴더를 그대로 제공하는 **신뢰되는 HTTPS 정적 주소**를 Safari로 엽니다. 서버는 파일만 전달하며 계산하지 않습니다. 이 산출물은 외부에 배포되어 있지 않습니다.
2. ‘오프라인 · iPhone 사용 안내’에서 **오프라인 저장 완료**를 확인합니다.
3. Safari 공유 메뉴 → **홈 화면에 추가** → 표시된다면 **웹 앱으로 열기**를 켜고 추가합니다.
4. 홈 화면 아이콘으로 한 번 연 뒤, 연결을 끊고 다시 열어 오프라인 실행을 확인합니다.
5. 이후에는 인터넷·계산 서버 없이 앱 내부 Worker에서 계산합니다.

초기 HTTPS 전달은 본인이 이미 사용하는 정적 호스팅이나 신뢰되는 로컬 HTTPS 환경을 사용할 수 있습니다. 도메인이나 외부 서비스를 앱 코드에 내장하지 않았습니다. 앱 계산에는 인터넷이 필요하지 않지만 **아무 초기 페이지 전달 수단도 없이 iPhone 파일 미리보기만으로 PWA 설치까지 완료하는 것은 보장할 수 없습니다.**

### B. 인터넷 없는 같은 Wi-Fi에서 PC 파일 전달

Python이 설치된 PC에서 `lotto-webapp` 폴더를 열어 실행합니다.

```console
python -m http.server 8000
```

- PC: `http://localhost:8000`
- 같은 Wi-Fi의 iPhone Safari: `http://PC의_로컬_IP:8000`

필요하면 PC 방화벽에서 해당 로컬 연결을 허용해야 합니다. 인터넷 연결은 필요하지 않습니다. 페이지가 열린 뒤 계산 자체는 iPhone에서 수행되므로 파일 전달 PC가 계산을 맡지 않습니다.

**iPhone의 `localhost`는 iPhone 자신입니다.** PC 서버에 접근할 때는 PC의 로컬 IP를 사용해야 합니다. `http://192.168…` 같은 LAN HTTP 주소는 PWA 서비스 워커가 요구하는 보안 컨텍스트가 아닙니다. 따라서 이 방식만으로 홈 화면 앱의 오프라인 재실행을 보장하지 않습니다. 페이지를 새로 열거나 새로고침하려면 파일 전달 서버가 다시 필요할 수 있습니다. PC의 `http://localhost`에서는 서비스 워커가 허용될 수 있지만 그 예외가 iPhone의 PC 접속 주소에 적용되지는 않습니다.

### iPhone 계산 중 유의점

- 충분한 터치 영역, 16px 이상 입력 글꼴, safe area 여백을 적용했습니다.
- 화면 깨우기 기능이 지원되고 허용되면 계산 중 요청합니다. 운영체제가 거절하면 계산 자체는 계속할 수 있습니다.
- 백그라운드 전환·잠금·메모리 압박으로 Safari가 계산을 정지하거나 탭을 종료할 수 있습니다. 이를 웹앱이 완전히 막을 수는 없습니다. 긴 계산은 화면을 켜둔 상태로 진행하세요.
- 진행 중 새로고침·페이지 닫기에는 계산을 이어받지 않습니다. 완료된 최근 결과만 저장합니다.
- 브라우저 저장 공간 정리, 비공개 모드, OS의 캐시 정리로 결과나 오프라인 파일이 사라질 수 있으므로 필요한 결과는 파일로 저장하세요.

## 화면에 표시하는 진행률

진행률은 **현재 전체 후보 스캔의 정확한 처리 비율**입니다. 초기화·10게임 greedy·각 슬롯 교체·최종 검산 등 스캔이 바뀌면 다시 시작합니다. local search 순회 횟수는 미리 정해져 있지 않으므로 전체 작업의 남은 시간이나 전체 완료율을 임의로 추정하지 않습니다. 경과 시간, 현재 초기해/슬롯/순회, 현재 C4/C5를 함께 표시합니다.

## Python 원본 분석과 포팅 대응

기존 `lotto_optimizer.py`, `test_lotto_optimizer.py`, `README_ko.md`, `requirements.txt`, 예시 결과를 읽고 다음 구조를 유지했습니다. 웹앱 사용에는 Python·NumPy·Numba가 필요하지 않습니다.

| 원본 | 웹 구현 |
|---|---|
| validate_input / passes_filters | validateInput / passesFilters |
| generate_universe, 전체 조합 생성 | generateUniverse + walk, 전체 C(45,6) 스트리밍 |
| 조합 순위 및 부분집합 집계 | 같은 combinadic rank와 Int32Array 집계 |
| calculate_N4 / calculate_N5 | neighbors의 ids4 / ids5 |
| CoverageState / _scores | CoverageState.score / best, 같은 포함배제 공식 |
| greedy_initial_solution | greedyInitialSolution, 모든 후보 전수 평가 |
| local_search | localSearch, 모든 후보 1장 교체를 수렴까지 반복 |
| 추가 초기해 | 고정 seed PRNG로 첫 후보만 변경한 뒤 같은 전체 greedy |
| evaluate_portfolio | 이웃 합집합 + 전체 U의 두 32-bit 마스크 독립 검산 |

**차이:** 재시작 난수 생성기는 NumPy PCG64 대신 JavaScript에 명시된 Mulberry32를 사용합니다. 따라서 추가 초기해와 최종 10게임이 Python과 다를 수 있습니다. 후보 순회는 원본과 같은 오름차순 사전식 순서이며, baseline greedy와 동일한 1장 교체의 동점 처리를 유지합니다. 같은 웹앱 버전·입력·설정·seed는 재현 가능합니다.

기본 첫 티켓은 N4 최대, 이후 티켓은 marginal C4 최대이며 동점이면 C5를 우선합니다. 1차 local search는 (C4,C5)를 사전식으로 개선합니다. 여러 초기해 중 최고 C4를 기록한 뒤, `ceil(995 × 최고 C4 / 1000)` 하한을 만족하는 초기해들에서 (C5,C4)를 개선합니다. 더 높은 C4를 채택하면 하한도 강화합니다. 개선이 없는 완전한 순회까지 반복하며 임의 시간 제한을 두지 않습니다. 2장 동시 교체는 원본과 마찬가지로 구현하지 않았습니다.

**전역 최적해 보장 없음.** 99.5%는 ‘탐색에서 얻은 최고 C4’ 기준이고 알려지지 않은 전역 최고값에 대한 보장이 아닙니다. 실제 합집합 크기를 기준으로 선택하며, 공통번호 개수나 1~45 사용빈도를 하드 규칙으로 제한하지 않습니다.

## 수학적 정확성과 메모리

아직 4+로 커버되지 않은 집합을 R4, 아직 5+로 커버되지 않은 집합을 R5라 합니다. 이 집합들에서 부분집합 S를 포함하는 조합 수를 집계합니다.

```text
marginal4(T) = Σ dR4(S), |S|=4 − 4 × Σ dR4(S), |S|=5 + 10 × 1[T∈R4]
marginal5(T) = Σ dR5(S), |S|=5 − 5 × 1[T∈R5]
```

R4와 R5는 별도로 관리합니다. 4개/5개/6개 정확히 일치하는 이웃을 한 번씩 열거하고 필터 통과 여부를 확인합니다. 추가/제거 시 참조 수가 0을 넘나드는 당첨조합만 부분집합 집계에 반영합니다.

- 전체 U는 약 1MB bitset으로 저장합니다. 8백만 개의 배열·객체를 생성하지 않습니다.
- 모든 조합 번호 배열, 전체 후보별 21개 부분집합 ID 배열, 후보 간 행렬을 저장하지 않습니다.
- 상태의 고정 TypedArray는 약 34MB입니다. 이웃 캐시는 최대 32개, 최종 검산용 bitset 약 2MB와 엔진/브라우저 메모리는 별도입니다.
- 큰 상태 배열은 재시작마다 새로 만들지 않고 같은 메모리를 초기화해 재사용합니다.
- 45개 번호 마스크는 두 개의 32-bit 정수로 계산합니다. JS 32-bit 연산으로 45개 비트를 한 번에 처리하거나 느린 BigInt를 사용하지 않습니다.
- Worker에서 계산하고, 131,072개 조합 단위 진행 알림을 제한된 빈도로 메인 화면에 보냅니다. 계산 중에도 UI·중단 버튼이 동작합니다.
- 최종 C4·C5는 U 전체를 순회한 값과 이웃 합집합이 일치해야 출력합니다.

메모리 절감은 탭 종료의 가능성을 낮추지만 모든 iPhone에서 종료되지 않는다는 보장은 아닙니다. 기기 실측을 하지 않았다면 iPhone 성능 수치를 주장하지 않습니다. 실제 검증 범위와 실행 시간은 `TEST_RESULTS_ko.md`를 확인하세요.

## 결과와 확률 해석

- C4: 10게임 중 하나라도 본번호 4개 이상 일치하는 서로 다른 W∈U의 수
- C5: 같은 정의로 5개 이상 일치하는 W∈U의 수
- P4=C4/|U|, P5=C5/|U|는 W가 U에 속하고 그 안에서 균등하다는 가정의 조건부 확률
- ‘정확히 4개’는 **10게임 중 최대 일치 개수**가 4개인 배타적 영역, 즉 C4−C5
- 정확히 5개는 C5−C6, 6개는 C6
- 본번호 5개 일치는 보너스에 따라 2등 또는 3등. 보너스 자체는 최적화하지 않음
- 게임별 marginal C4는 출력 순서에 따른 기여도. 합계는 C4
- 113,500/|U|는 필터·게임 간 중복을 무시한 참고 상한
- C4/8,145,060은 ‘U 안에 있고 4+ 일치’하는 결합확률. U 밖 당첨을 포함한 실제 무조건부 4+ 확률과 다름

이 전략은 전체 영역 일부를 포기하고 특정 영역에 집중하는 것이며, 필터로 무조건부 당첨확률이 증가했다고 해석하면 안 됩니다.

## 파일 구조와 테스트 재실행

```text
lotto-webapp/
  index.html
  style.css
  app.js
  worker.js
  manifest.json
  service-worker.js
  icons/
  README_ko.md
  TEST_RESULTS_ko.md
  tests/
```

실행에는 빌드 도구가 필요하지 않습니다. 테스트만 재실행하려면 Node.js를 사용합니다.

```console
node --test tests/engine.test.cjs
node tests/full-run.cjs
```

`tests/python-reference.json`은 Python 원본으로 생성한 작은 공간 비교값이고, `tests/full-result.json`은 JavaScript 전체 공간 실행 결과입니다. 배포용 코드 자체에 테스트 결과를 최적화 답으로 내장하지 않았습니다.

앱을 수정해 새 버전을 배포한다면 `service-worker.js`의 캐시 버전도 바꾸세요. 열려 있는 계산 화면을 강제 갱신하지 않도록 새 서비스 워커는 이전 앱 창들이 닫힌 후 활성화됩니다.
