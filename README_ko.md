# 로컬 로또 6/45 웹앱 — 고정 9조건

2026-09-10 개정. 기존 앱의 UI, 브라우저 계산 구조와 당첨번호 IndexedDB를 유지한 수정판입니다. 기본 당첨 데이터는 공식 출처의 1~1240회 본번호이며, 2026-09-10 공식 JSON 최신 회차를 재확인했습니다. 보너스는 필터나 최적화에 사용하지 않습니다.

## 실행

PC에서는 폴더 전체를 보관하고 index.html을 Chrome/Edge로 열 수 있습니다. file:// 모드는 계산용 Blob Worker와 기본 데이터 파일을 사용합니다. 기기 정책상 파일에서 Worker를 막는 경우 HTTPS 정적 사이트 또는 localhost 정적 파일 서버로 여세요. 계산용 서버·계정·외부 라이브러리는 필요하지 않습니다.

iPhone은 Safari로 HTTPS 페이지를 열고 ‘공유 → 홈 화면에 추가’를 사용합니다. 처음에는 연결이 필요하며 ‘오프라인 저장 완료’ 이후에는 연결 없이 다시 열고 계산할 수 있습니다. 파일 앱 미리보기는 웹앱 실행 환경과 다릅니다. 계산 중 화면을 열어두세요. 다른 앱으로 이동하면 iOS가 계산을 일시 중지하거나 페이지를 종료할 수 있습니다.

실전 모드에서는 DB 최신 회차가 직전 회차이며, 그 다음 회차의 10게임을 생성합니다. 입력할 직전 번호는 없습니다. DB가 아직 갱신되지 않았을 때는 화면의 생성 대상 회차를 확인하고 당첨번호를 갱신하세요. 추첨 전 미래 회차를 수동 입력하지 마세요.

## 고정 필터 — 순서대로 모두 ON

1. 역대 1등과 본번호 6개가 정확히 동일한 조합 제외. 순서는 무시하며 5개만 같으면 이 조건은 통과합니다.
2. 정렬한 6개가 완전 등차수열이면 제외.
3. 직전 회차와 3개 이상 중복이면 제외. 0~2개 허용.
4. n, n+1, n+2의 3연속 이상이면 제외. 2연속 자체는 허용.
5. 최대 인접간격은 20 이하. 20은 통과, 21은 제외.
6. 인접간격 3 이하가 최대 2개. 3개부터 제외.
7. [1~11], [12~22], [23~33], [34~45] 중 한 구간에 4개 이상이면 제외.
8. 최댓값−최솟값이 15 이하이면 제외. 차이 16부터 통과.
9. 전부 홀수 또는 전부 짝수만 제외. 홀짝 5:1과 1:5는 이 조건에서 허용.

전체 C(45,6)=8,145,060개에 9조건을 적용해 Universe U를 확정한 뒤 최적화를 시작합니다. 최종 티켓도 U에서만 선택합니다. 독립 제거 수는 다른 조건을 무시한 해당 조건 단독 수치입니다. 순차 추가 제거 수는 앞 조건들을 통과한 후보 중 그 조건이 처음 제거한 수치입니다. 두 비율은 전체 8,145,060개를 분모로 사용합니다. 독립 수치는 서로 겹치므로 합산하지 않습니다. 순차 수치 합계 + U = 전체 조합입니다.

필터는 사용자가 후보 범위를 선택하기 위한 규칙입니다. 과거 당첨조합이 다시 나오지 않는다는 확률 법칙은 없습니다. 조건부 커버율은 당첨조합이 U 안에 있다는 가정이며, 필터가 실제 무조건부 당첨확률을 높인다는 의미가 아닙니다.

## 최적화와 정확 계산

- C4 = U 중 10게임 중 어느 하나와 4개 이상 일치하는 서로 다른 조합의 수.
- C5 = 동일하게 5개 이상 일치하는 서로 다른 조합의 수.
- 매 선택에서 U 전체 후보를 평가하는 greedy, 다중 초기해, 모든 U 후보를 대상으로 한 1장 교체 local search를 유지했습니다. 후보 샘플링이나 게임 간 겹침 상한은 없습니다.
- 먼저 C4를 개선하고, 탐색 중 발견한 최고 C4의 99.5% 이상인 범위에서 C5를 개선합니다. C4/C5가 모두 같은 동률에서는 게임 간 공통번호 총합이 작은 쪽을 선택합니다. 이 선호 때문에 커버리지 우선순위가 바뀌지 않습니다.
- 추가 재시작은 기본 2회, seed는 20260908입니다. 동일 DB·모드·대상·재시작·seed이면 같은 티켓과 집계를 재현합니다. 실행 시간과 생성 시각은 달라집니다.
- 마지막에 U의 모든 조합을 10게임과 직접 비교해 C4/C5를 다시 계산합니다. 증분 커버리지와 다르면 결과를 반환하지 않습니다.
- 후보 전수 스캔 수, local search 순회 수, 채택한 교체 수를 상세 화면에서 확인할 수 있습니다.

99.5%의 기준은 증명된 전역 최고가 아니라 탐색 중 발견한 최고입니다. 전역 최적해를 보장하지 않습니다. 기기 성능과 수렴 과정에 따라 수분 이상 걸릴 수 있습니다. 메인 화면과 별도 Worker에서 계산하며 중단 버튼을 제공합니다.

## 백테스트

생성 모드를 ‘과거 회차 검증’으로 바꾸고 발표된 회차 t를 지정합니다. t=800이라면 과거 동일조합 목록은 1~799회, 직전 번호는 799회만 사용합니다. Worker에 800회와 이후 기록을 전달하지 않습니다. 실제 800회 결과는 10게임 생성이 끝난 뒤 화면에서만 비교합니다. 이후 데이터가 추가되어도 과거 백테스트의 입력은 바뀌지 않습니다. 1~t−1에 누락이나 충돌이 있으면 복구를 안내합니다.

## 당첨번호 업데이트와 보존

데이터 메뉴는 최신 저장 회차, 총 회차 수, 연속 범위, 마지막 온라인 확인·시도, 마지막 성공 갱신, 출처를 표시합니다. 최신 확인, 수동 추가, JSON 가져오기/내보내기를 제공합니다.

앱은 먼저 기본 파일과 IndexedDB로 준비되어 네트워크와 독립적으로 계산할 수 있습니다. 온라인에서는 같은 사이트의 최신 lotto_history.json을 확인하고, 동행복권 공식 JSON에서 최신 회차를 조회합니다. 이미 있는 회차는 재다운로드하지 않으며 누락·신규 회차만 모읍니다. 공식 조회는 요청 회차 주변 묶음을 반환하므로 응답의 다른 회차도 재사용합니다. 공식 JSON이 차단되거나 실패하면 공개 GitHub 회차별 JSON 미러를 사용합니다. 공식 출처가 확인한 최신 회차보다 미러가 뒤처지면 불완전한 갱신으로 처리합니다.

모든 입력 경로는 shared.js의 같은 검증 함수를 사용합니다. 회차별 본번호가 정확히 6개의 서로 다른 1~45 정수인지 검증하고 오름차순으로 정규화합니다. 같은 회차·같은 번호는 한 건만 저장합니다. 같은 회차·다른 번호는 충돌 오류이며 덮어쓰지 않습니다. 다운로드 전체를 검증한 뒤 하나의 IndexedDB 트랜잭션으로 저장합니다. 일부 다운로드나 저장이 실패하면 해당 신규 묶음 전체가 반영되지 않습니다.

IndexedDB 이름 local-lotto-history, 버전 1, draws/meta 저장소를 그대로 유지합니다. PWA 캐시 업데이트에서 DB를 삭제하거나 초기화하지 않습니다. 기본 파일은 없는 회차만 보완하며 로컬 기록과 충돌하면 기존 기록을 보존하고 경고합니다. 저장소가 제한된 환경은 기본 DB로 계산하고 추가 기록은 세션 동안만 보관하므로 JSON으로 내보내세요. 브라우저의 사이트 데이터 삭제·저장 공간 자동 정리는 앱 업데이트와 달리 영구 저장을 지울 수 있습니다. 동일 기기라도 도메인·프로토콜·포트가 달라지면 별도 저장소이므로 이동할 때 JSON을 가져오세요.

- 공식 회차 JSON: https://www.dhlottery.co.kr/lt645/selectPstLt645InfoNew.do?srchDir=center&srchLtEpsd=1240

## GitHub Pages 업로드와 자동 갱신

lotto-webapp 폴더의 **내용 전체**를 저장소 웹 루트에 올립니다. .github/workflows/update-lotto-history.yml은 저장소 루트의 .github/workflows 아래에 있어야 합니다. 숨김 폴더도 포함하세요. 아래 파일들이 같은 버전이어야 합니다.

- index.html, style.css, app.js, worker.js, shared.js, providers.js, history.js
- lotto_history.json, history-data.js, history-provenance.json
- service-worker.js, manifest.json, icons/ 전체
- scripts/update-history.cjs, tests/nine.test.cjs, tests/browser-nine.cjs, tests/verify-full.cjs, tests/compat-nine.cjs
- .github/workflows/update-lotto-history.yml, .gitignore, README_ko.md, HISTORY_UPDATE_ko.md, TEST_RESULTS_ko.md

/korean-lotto-/ 같은 하위 경로를 지원합니다. manifest·Worker·기본 JSON·서비스 워커 경로는 상대경로입니다. 서비스 워커는 코드 묶음을 버전별로 보관하고, 당첨번호 JSON은 network-first로 확인합니다. 새 서비스 워커는 사용자가 ‘새 앱 적용’을 누르거나 기존 창들이 닫힐 때 활성화하며, 계산 중 적용을 막습니다. 활성화 후 이전 앱 캐시를 정리해도 IndexedDB는 유지합니다. 코드 배포 때 service-worker.js의 CACHE 버전도 변경하세요. JSON만 갱신하는 경우 캐시 버전을 올릴 필요가 없습니다.

GitHub Actions는 토요일 22:15 한국시간(13:15 UTC)에 실행하며 Actions → Update lotto history → Run workflow로 수동 실행할 수 있습니다. 일정은 GitHub 실행 대기 때문에 지연될 수 있습니다. 기본 브랜치를 체크아웃하고 단위 테스트를 실행한 뒤 공식 출처만 사용해 신규 회차를 모읍니다. 전체 형식·회차 연속성·충돌 검증에 실패하면 파일을 수정하지 않습니다. 신규 회차가 있을 때만 JSON·파일 실행용 JS·출처 정보를 함께 갱신하고 자동 커밋합니다. 브랜치 보호 정책이 봇 push를 금지하면 작업은 실패 상태로 표시되며 정책을 우회하지 않습니다.

저장소에는 위 자동 커밋 파일만 추가했으며 실제 GitHub 계정에 배포하거나 저장소 설정을 변경하지 않았습니다. GitHub 기본 GITHUB_TOKEN으로 만든 커밋은 일반 브랜치 기반 Pages 빌드를 자동 실행하지 않습니다. 기존 Pages 배포 workflow가 없다면 변경 커밋 후 Pages 배포를 수동 실행해야 사이트의 기본 JSON도 갱신됩니다. 이번 파일은 Pages 배포 권한을 추가하지 않습니다. 브라우저 자체의 공식 JSON → IndexedDB 갱신은 Pages 재배포 없이 작동합니다.

관련 GitHub 설명: https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site

## 테스트 실행

Node.js 22 이상에서 앱 폴더를 작업 디렉터리로 사용합니다.

```text
node --test tests/nine.test.cjs
node scripts/update-history.cjs
node tests/browser-nine.cjs
node tests/verify-full.cjs
node tests/compat-nine.cjs
```

브라우저 테스트에는 Playwright와 Microsoft Edge가 필요합니다. Playwright를 다른 곳에 설치했다면 PLAYWRIGHT_MODULE에 모듈 경로를 지정하세요. 테스트가 임시 정적 서버와 독립 브라우저 프로필을 만들기 때문에 사용자 앱 DB를 건드리지 않습니다. 결과는 tests/evidence-nine/에 저장하며 Git에 올릴 필요가 없습니다. browser-nine.cjs의 실제 온라인·전체 계산 테스트는 제공 시점 기본 데이터 1240회를 기준으로 합니다. 기본 데이터가 증가하면 이 브라우저 시나리오의 예상 최신 회차도 갱신하세요. 단위 테스트는 새 회차 증가를 허용합니다.

원본 5조건 및 이전 6조건 테스트는 최신 필터의 기대값과 다르므로 이번 배포 테스트에서 분리했습니다. 실제 결과와 확인하지 못한 환경은 TEST_RESULTS_ko.md에 기록합니다.
